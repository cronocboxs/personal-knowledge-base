# config-py 解析ノート

## 1. 概要・目的

このファイル（`config-py.py`）は、プロジェクト全体における各種ファイルシステムパス、外部サービス（LLMプロバイダーなど）の接続設定、およびデフォルトの設定値（`DEFAULT_CONFIG`）を一元管理する、システム起動時の初期設定ファイルです。

主な目的は以下の通りです。
1. **パスの一元化**: ハードコードされがちなファイルやディレクトリの絶対パスを定義し、構造の可読性と保守性を高める。
2. **初期化**: 設定ファイルが存在しない場合や読み込みに失敗した場合に、動作可能なデフォルト設定を自動的に書き出し、運用を可能にする。
3. **APIキーの安全な取得**: 複数の場所に設定が分散している可能性を考慮し、APIキーの読み込み処理で高い信頼性を確保する。

## 2. 主要コンポーネント・関数

### A. パス定義 (Path Definitions)
コードの冒頭で、以下の重要ディレクトリの絶対パスが定義されています。
* `SCRIPT_DIR`: 本ファイル自身のディレクトリパス。
* `PROJECT_ROOT`: プロジェクトのルートディレクトリ（根拠となる共通パス）。
* **各種専用ディレクトリ**: `CONFIG_PATH` (設定ファイル)、`PRIVATE_DIR` (機密情報)、`RULES_DIR` (規約)、`RESOURCES_DIR` (資源)、`KNOWLEDGE_DIR` (ナレッジ) など、プロジェクト全体のコアフォルダへの参照を確立しています。

### B. デフォルト設定 (`DEFAULT_CONFIG`)
使用するLLMプロバイダー（Gemini, Ollama）のデフォルトモデル名や、接続エンドポイントを定義しています。これにより、設定ファイル（`settings.json`）が空でも、次に利用可能な構造を持つ最低限の環境が担保されます。

### C. `load_config() -> dict`
1. **読み込み試行**: `CONFIG_PATH` を参照し、既存の `settings.json` の読み取りを試みます。
2. **エラーハンドリング**: 読み取りが成功すればその内容を返却します。
3. **初期化**: 読み取りに失敗した場合（例: ファイルが存在しない、JSON形式のエラー）、`DEFAULT_CONFIG` の内容でファイルを作成し直し、そのデフォルト設定を返却します。
これは、**「設定ファイルが存在しない場合でも、必ず有効な構造のファイルが存在する状態を保証する」**ための重要なロジックです。

### D. `get_gemini_api_key() -> str`
Gemini APIキーを安全かつ確実に取得するためのヘルパー関数です。以下の優先順位でキーを検索します。
1. **専用ファイル検索**: `PRIVATE_DIR` 内の `gemini_api_key.txt`、`gemini-api-key`、`api_key.txt` という複数の候補ファイルから読み込みを試みます。
2. **環境変数**: 上記のファイル検索に失敗した場合、OSの環境変数 `GEMINI_API_KEY` を利用します。
この多重チェックを行うことで、デプロイ環境やローカル環境の違いに起因するAPIキーの欠落を防ぎます。

## 3. 処理フローと実装ポイント

### 構造化された依存関係の構築
本ファイルは、プロジェクトのすべての主要なサブシステム（`00-rules`, `01-private`, `04-resources`, `02-knowledge`）がどこに存在するかという「地図」を定義する役割を担っています。このパス定義が正しいことが、以降の全ての処理の前提となります。

### 設定の強制初期化（Self-Healing Logic）
最も重要な実装ポイントは `load_config()` のエラー処理です。単に存在チェックを行うだけでなく、**「もし読み込みに失敗したら、適切なデフォルト値をすぐに書き込んでしまう」**という仕組みを採用することで、運用上「設定ファイルが空で動けない」という障害を未然に防いでいます。

### セキュリティ上の工夫
`get_gemini_api_key()` 関数が複数のファイル名パターンや環境変数を参照することは、プラクティスとして推奨される高度な対応です。秘密鍵（APIキー）を一つの場所に限定せず、利用シーンに応じた複数箇所から読み込めるようにしておきつつ、読み込み失敗時に速やかに次の候補へ移行するロジックは、セキュリティと耐障害性のバランスを取る良い設計です。
