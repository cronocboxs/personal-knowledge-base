# 役割

`04-resources/git-repository/<リポジトリ名>/` 内のソースコード全域を技術スタック（言語・フレームワーク・アーキテクチャ）問わず自動検知・スキャンし、**エントリーポイント、UI/API/CLIインターフェース、操作・呼び出しトリガーに対する内部処理と状態変化**を `02-knowledge/<リポジトリ名>/` 配下に網羅的に蓄積し、Git コミットまで完了させる。

---

## 前提条件（共通ルールの確認）

- 作業開始時に、リポジトリルート直下の `AGENTS.md` および `00-rules/workflow.md` を必ず読み込み、そこに記載された「絶対遵守ルール」「ディレクトリ編集ポリシー」「ナレッジ育成ルール」に従うこと。

---

## 知識進化（Knowledge Evolution）判定規則

`02-knowledge/<リポジトリ名>/` 内のノートの Frontmatter (`phase`) を更新する際は、**リポジトリ全体の機能網羅率**を基準に判定すること。

| Phase | 判定基準 | 今回実行すべき解析・蓄積タスク |
| :--- | :--- | :--- |
| **Phase 1** | 未作成または `phase: 1` 指定 | **Phase 1 (言語・技術スタック判定と機能全域の目録化)**: パッケージ構成・設定ファイルから技術スタック（Web/API/CLI/Lib等）を特定し、全エントリーポイント/ルーティング/モジュールを特定して `overview.md` を作成。全機能を `unexplored_domains` に登録する。 |
| **Phase 2** | 未解析領域（`unexplored_domains`）が存在する | **Phase 2 (機能・トリガー別処理トレース)**: `unexplored_domains` に残っているソースコードを開き、**各トリガー（ボタン操作/APIリクエスト/CLIコマンド/関数呼び出し）に対するパラメータ評価、内部ビジネスロジック、データ永続化/外部連携、応答・状態変化**を解読して本文に追記。完了した機能から順次 `unexplored_domains` から除外する。 |
| **Phase 3** | 全機能の挙動解読が完了 (`unexplored_domains` が空) | **Phase 3 (コンポーネント間連携・例外・設計パターンの解読)**: モジュールを跨ぐデータ流転、エラー・例外系ハンドリング、認証/認可制御、アーキテクチャ設計原則の抽出・追記。 |

---

## 仕事

- **実行手順**:
  1. **技術スタック判定と全件インデックス作成（Phase 1）**:
     - リポジトリ構造、パッケージ定義（`package.json`, `composer.json`, `Cargo.toml`, `go.mod`, `pyproject.toml`, `Makefile` 等）を確認し、技術スタックとリポジトリ種別（Webアプリ, REST/GraphQL API, CLI, ライブラリ, マイクロサービス等）を自動判定する。
     - 入力口（ルーティング定義、コマンド定義、公開API、UIコンポーネント、モジュールエントリーポイント）を全件収集・リスト化し、`02-knowledge/<リポジトリ名>/overview.md` にまとめる。
  2. **未解析リスト（`unexplored_domains`）の登録**:
     - 洗い出した全領域・全モジュールを `overview.md` および各ノートの Frontmatter 内 `unexplored_domains` に登録する（例: `["認証機能/API", "データ処理Worker", "CLIインターフェース", ...]`）。
  3. **トリガー別・処理シナリオの追跡（Phase 2）**:
     - `unexplored_domains` から未解析モジュールを選択し、該当ソースコードを直接閲覧（`read`/`view`）する。
     - 操作・呼び出しトリガー（画面操作、API呼び出し、CLI実行、関数コール）から、**パラメータ入力 ➔ ドメインロジック/状態変化/DB・外部連携 ➔ 出力/レスポンス/UI変化** への一連の処理の流れをトレースして本文に詳細記述し、書き込みが完了したドメインのみ `unexplored_domains` から除外する。
  4. **Phase判定とコミット**:
     - `unexplored_domains` に未解析領域が残っている場合は `phase: 2` を維持する。**全領域の解読・本文記述が完了して空（`[]`）になった場合のみ `phase: 3` に引き上げる。**
     ```bash
     git add 02-knowledge/<リポジトリ名>/
     git commit -m "auto(doc): <リポジトリ名> の機能・処理挙動ナレッジを追加・更新 (未解析残: X件)"
     ```

- **必須記述フォーマット（02-knowledge 配下のノート構造）**:

  ※リポジトリの性質（Web/API/CLI/ライブラリ等）に応じて用語を適合させて記述すること。

  ```markdown
  ---
  created: YYYY-MM-DD
  updated: YYYY-MM-DD
  tags: [repository-name, spec, code-analysis]
  phase: 2 # リポジトリ内の全機能・全インターフェースの解読が完了するまで絶対に 3 にしないこと
  status: active
  unexplored_domains:
    - "モジュール/機能A (`path/to/source_a`)"
    - "APIエンドポイント/コマンドB (`path/to/source_b`)"
  ---

  # [モジュール/ドメイン名] 挙動・処理仕様ナレッジ

  ## 1. 識別された機能・インターフェース一覧 (Phase 1)
  - [x] 機能/エンドポイントA (`path/to/source_a`)
  - [ ] 機能/エンドポイントB（未解析）

  ## 2. インターフェース・トリガー別詳細トレース (Phase 2 必須)

  ### 機能1: [対象機能/画面/API/コマンド名]
  #### トリガー1: 「[操作・呼び出しトリガー (例: ボタン押下 / POST /api/v1/xxx / CLIコマンド等)]」
  - **全てのファイルの読み込み**:
    - ルートからコントローラー、サービスやモデル/ビューなど。
    - ライブラリなどの付随処理も全て。
  - **入力・要求（Input/Request）**:
    - 受取パラメーター、ヘッダー、フォーム入力値、CLI引数、環境変数など。
  - **内部処理流転（Execution Flow）**:
    1. 入力バリデーション・認可チェック。
    2. ビジネスロジック処理・ドメインイベント発火。
    3. データ構造の変化（DB保存、キャッシュ更新、ファイル書き出し、外部API呼び出し）。
  - **出力・応答・状態変化（Output/Response/State Change）**:
    - **成功時**: 戻り値、HTTPステータス/レスポンスBody、画面遷移・トースト表示、ログ出力。
    - **失敗時**: エラーハンドリング、例外応答、ロールバック挙動。

  ## 3. モジュール間連携・例外ハンドリング・設計パターン (Phase 3 必須 - 全機能完了後)
  - **コンポーネント間・ドメイン間の相互作用**: モジュールAでの処理が、他モジュール/非同期Worker/他サービスへ与える副作用や波及影響。
  - **横断的関心事**: 共通エラーハンドリング、認証・認可基盤、ロギング・モニタリング設計。

- **やらないこと**:
  - 特定の画面や代表的な機能（ログイン、サンプルコード等）だけを記述して「リポジトリ全体の解読・ナレッジ蓄積が完了した」と誤認すること。
  - プロジェクト構成・ソースコード全域を走査せずに、一部のファイルのみやファイル名からの推測だけでナレッジ作成を終わらせること。
  - `unexplored_domains` に未解析の機能・インターフェース・モジュールが残っている状態で `phase: 3` を宣言すること。
  - 本文（`2. インターフェース・トリガー別詳細トレース`）の加筆を行わずに Frontmatter の未解析リストだけを消去すること。
  - `04-resources/` 内の一次情報原本の改変・直接編集・削除。
  - 暗号鍵、APIキー、環境変数（.env）、絶対パス等の機密・セキュリティ情報の書き出し。

- **絶対にやってはならない不正判定（アンチパターン）**:
  - 本文の処理トレース記述を追加更新せず、Frontmatter の `unexplored_domains` を空（`[]`）にして手抜きで Phase 3 に昇進させること。
  - `app`, `Controller`, `Service`, `Job`, `Model` などの配下に多数の処理ファイルが存在するにもかかわらず、`unexplored_domains: []`（空）にして安易に Phase 3 へ引き上げること。

- **入力**:
  - `04-resources/git-repository/<リポジトリ名>/clone/<ブランチ>/` 配下のソースコード全域

- **出力先**:
  - `02-knowledge/<リポジトリ名>/` 配下の Markdown ファイル群（`overview.md`, `architecture.md`, `features.md` 等）

- **終わりの条件**:
  - リポジトリ内に存在するすべての機能・トリガー（UI/API/CLI/関数）に対する挙動・データ推移・内部処理フローが網羅的に解読・記録されたこと。
  - `unexplored_domains` が空（`[]`）になり、Frontmatter の `phase` が `3` へ引き上げられた状態で `git commit` が正常完了した時点。

- **止まる条件**:
  - `04-resources/git-repository/<リポジトリ名>/` 配下に対象コードが存在しない場合。
  - API のレートリミット（`Rate limit exceeded`）が発生した場合。
  - `pre-commit` フック等でエラーが発生し、自動修復が不可能な場合。

- **レートリミット・エラーハンドリング**:
  - API 制限（Quota / Rate limit）が発生した場合は、その時点で作成・更新が完了しているファイルのみを保存し、次回実行時に `unexplored_domains` に残っている領域からスムーズに再開できるよう進捗ログを出力して安全に終了すること。
